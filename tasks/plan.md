# 股票模拟交易系统实施计划

> 状态：待人工审批
>
> 本计划依据已确认的 `CAPABILITY_MAP.md`、`SPEC.md` 与 12 个模块规格编制。本文件只定义实施顺序，不表示任何产品代码、测试或外部发布已经完成。

## 1. 计划目标

以可独立验证的纵向切片交付完整模拟交易应用，同时把账户种子资产、撮合原子性、资金与股票守恒、WebSocket 隔离和断线恢复等高风险能力提前验证。正式执行清单位于 `tasks/todo.md`。

## 2. 模块关系

| 提供模块 | 主要输出 | 直接消费者 |
|---|---|---|
| `runtime-foundation` | 工作区、命令、构建与进程生命周期 | 全部模块 |
| `market-simulation` | 股票种子配置、不可变基准价、实时行情 | `account-ledger`、`order-book`、`realtime-sync`、`trading-web` |
| `identity-session` | 用户、Cookie 会话、注册账户初始化 | `account-ledger`、全部私有 API 与 WebSocket |
| `account-ledger` | 现金、可用/冻结持仓、平均成本、总资产 | `order-book`、`matching-engine`、`trading-web` |
| `order-book` | 限价单、价格时间排序、资源预占 | `matching-engine`、REST、WebSocket、前端 |
| `matching-engine` | 成交、订单状态、资金与股票转移 | `realtime-sync`、REST、前端 |
| `realtime-sync` | 公共行情事件与私有交易事件 | `trading-web`、`reconnect-recovery` |
| `trading-web` | 认证、行情、委托、账户与成交界面 | `delivery-evidence`、浏览器验收 |
| `matching-test-suite` | 确定性回归与覆盖率门禁 | 独立审查、最终验证 |
| `containerized-runtime` | 可复现生产容器 | 最终验收与交付 |
| `delivery-evidence` | README、架构决策、Prompt 与发布证据 | GitHub 发布 |

## 3. 关键架构决策

- 使用 npm workspaces 管理 `apps/web`、`apps/server`、`packages/shared`，共享 DTO 先于消费者稳定。
- 后端为单进程模块化单体，所有内存写操作在一个同步事务边界内完成，避免账本和订单半更新。
- 金额使用整数分；股票数量使用安全整数；注册种子成本只读取不可变种子基准价。
- 用户获得 100 万初始现金及每支种子股票 1,000 股；种子资产不产生委托或成交。
- 行情只更新估值和展示，不参与撮合；注册后股票只在用户成交间转移。
- REST 快照是恢复权威，WebSocket 是增量通道；连接世代防止旧事件覆盖新状态。
- 测试优先使用注入时钟、随机源、id 与序号，禁止依赖真实等待和不确定随机结果。

## 5. 分阶段执行顺序

### 阶段一：基础与高风险领域内核

1. `T01` 建立工作区与包边界。
2. `T02` 建立静态检查和测试命令。
3. `T03` 固定共享契约、金额与股票种子模型。
4. `T04` 建立可测试服务器生命周期。
5. `T05` 实现注册账户种子资产与账本。
6. `T06` 实现委托簿和资源冻结。
7. `T07` 实现撮合与结算原子事务。
8. `T08` 完成撮合不变量与覆盖率矩阵。

检查点：共享契约可编译；种子成本可复现；禁止裸卖空；价格时间优先、部分成交、资金和股票守恒均有确定性测试。

### 阶段二：认证、行情与 REST 纵向切片

9. `T09` 建立前端壳、API 客户端和快照状态容器。
10. `T10` 完成注册、登录、会话恢复和初始账户快照纵向切片。
11. `T11` 完成模拟行情 REST 与行情看板纵向切片。
12. `T12` 完成下单、查询、撮合和快照 REST 纵向切片。
13. `T13` 完成交易表单与委托列表纵向切片。
14. `T14` 完成资金、持仓、总资产和成交记录纵向切片。

检查点：用户能从 UI 注册登录、看到确定性种子资产和实时行情，并通过 REST 完成双用户交叉委托及状态查询。

### 阶段三：实时通信与恢复

15. `T15` 完成公共行情 WebSocket。
16. `T16` 完成私有委托、持仓和成交事件。
17. `T17` 完成双用户 REST/WebSocket 集成测试与隔离验证。
18. `T18` 完成断线重连、世代保护和快照恢复。
19. `T19` 完成连接、错误、空态、窄屏和键盘体验。

检查点：公共与私有事件正确隔离；断线期间交易可通过重连快照恢复；无重复连接或旧事件覆盖。

### 阶段四：生产运行与浏览器验收

20. `T20` 完成生产构建、静态页面与单进程启动。
21. `T21` 完成非 root 多阶段 Docker 构建和 Compose 健康检查。
22. `T22` 完成双浏览器上下文核心撮合验收。
23. `T23` 完成断线恢复、刷新恢复和窄屏浏览器验收。

检查点：本地生产模式与容器模式均能提供页面、REST 和 WebSocket；Playwright 断言具体业务值。

### 阶段五：证据、审查与发布

24. `T24` 完成 README 与架构决策说明。
25. `T25` 完成真实 Prompt 记录和验证记录框架。
26. `T26` 执行独立多维代码审查；如有阻断问题，先增加小型修复任务，不得直接扩大本任务。
27. `T27` 执行最终完整验证并记录真实结果。
28. `T28` 准备 GitHub 发布材料并复核远程、分支和 Secrets。
29. `T29` 仅在用户明确授权后执行普通 push 并核验公开链接。

最终检查点：所有验收条件有证据，独立审查无未解决阻断项，GitHub 发布严格位于全部验证之后。

## 6. 纵向切片策略

- 认证切片贯穿用户服务、Cookie API、前端表单、会话恢复和初始账户快照。
- 行情切片贯穿种子配置、可控模拟器、REST、WebSocket 与看板。
- 交易切片贯穿资源校验、委托簿、撮合、账本、REST、UI 与双用户验收。
- 恢复切片贯穿连接管理、快照、状态替换、世代保护和 Playwright 断网场景。
- 文档与发布切片只记录真实实现和验证，不提前声称成功。

## 7. 并行与顺序约束

- `T05` 与 `T09` 在 `T03/T04` 稳定后可并行，但共享契约改动必须先协调。
- `T10` 与 `T11` 可在基础 API 和前端壳稳定后并行。
- `T24` 的结构可提前准备，但架构决定和命令验证只能在 `T23` 后定稿。
- `T06 → T07 → T08`、`T12 → T13 → T14`、`T15 → T16 → T18` 必须顺序执行。
- `T26 → T27 → T28 → T29` 严格串行；任何阻断审查发现都会阻止发布。

## 8. 风险与缓解

| 风险 | 级别 | 提前措施 |
|---|---|---|
| 初始持仓误用波动价导致成本不确定 | 高 | `T03/T05` 固定不可变基准价并用不同当前价做复现测试 |
| 卖单冻结或部分成交破坏数量守恒 | 高 | `T05`～`T08` 先写不变量测试，再接 API/UI |
| 撮合失败产生半更新 | 高 | 单一同步事务、失败快照对比、原子性测试 |
| WebSocket 私有事件泄露 | 高 | `T16/T17` 使用两个用户连接验证负向隔离 |
| 重连发生竞态和重复应用 | 高 | 连接世代、单重连循环、快照期间缓冲及浏览器断网验收 |
| TypeScript 7 生态兼容 | 中 | `T01/T02` 最早安装并运行最小编译；阻断时先更新规格再换版本 |
| Secure Cookie 与本地 HTTP 冲突 | 中 | Cookie 的 `Secure` 由实际 HTTPS 配置控制，并在集成测试覆盖开发/生产配置 |
| Docker 与本地脚本不一致 | 中 | 容器调用同一生产构建和启动入口 |
| 文档宣称未经验证结果 | 中 | `T24/T25` 只写命令与待验证项，`T27` 后填真实结果 |
